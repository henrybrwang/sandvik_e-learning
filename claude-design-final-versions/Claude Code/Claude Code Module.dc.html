Claude Code

Claude Code is the agentic coding experience for reading and changing a codebase, running commands, working with tests, and supporting development inside the terminal and your editor. This module shows you when to reach for it, how powerful it is, and the engineering judgement that turns a working demo into something Sandvik can rely on.

Claude can accelerate your work, but you remain responsible for what you enter, approve, run, share and publish. Follow Sandvik policy, protect sensitive information, and review outputs before relying on them.

What this module is about
Claude Code can do a great deal. The harder skill is knowing how much knowledge, design and review a real application actually needs. This module keeps two ideas side by side: smaller work such as one time scripts, throwaway tools, learning and prototypes is genuinely encouraged for everyone, while work that other people will depend on needs the same engineering process you would apply to any Sandvik system.

Tool fit

Claude Code is for work that lives in a codebase. It reads and changes files, runs commands, works with tests, and uses developer tools. Choosing the right product is the first decision.

How to think about Claude Code

Claude Code is powerful. It can build something that runs in minutes. The trap is believing that a working demo is the same as a real, dependable application.

Software that other people rely on carries weight that a demo does not: edge cases, data handling, security, performance, maintenance, and the question of who owns it when it breaks. None of that disappears because Claude wrote the first version quickly.

Encouraged for everyone

If you are not a developer, you are welcome to explore. Small scope work is a great way to learn and to solve your own problems.

›Single use scripts and quick helpers.
›Throwaway tools and learning exercises.
›Prototypes that nobody depends on yet.
Needs real engineering

As soon as something matters or others rely on it, casual building is not enough on its own.

›Systems other people use without checking.
›Anything touching important or sensitive data, payments, or access.
›Anything that integrates with business systems.
The central skill

The skill is not letting Claude write code. It is deciding what kind of work this is, giving Claude enough specification and context, and then putting the result through the same quality, security and release process you would apply to code a person wrote.

It is common for non developers to underestimate how many design decisions a developer actually makes along the way. When you do not make those decisions yourself in the prompt, Claude will take liberties and decide for you. On a small script that is usually fine, but at a larger scale those quiet assumptions add up and can give the wrong complete picture.
Working with Claude Code · 1 of 6

Match effort to intent

Before you start, decide what kind of work this is. That single decision sets how much process, review and care it needs.

Throwaway
A quick local helper you will run once or twice. Keep it free of secrets and real data. Casual building is fine.
Experimental
A prototype to learn or test an idea. Still low risk, as long as nobody relies on it and the data is not sensitive.
Shared
Other people will use it. Now it needs an owner, review, tests, and a clear view of the data it touches.
Bound for production
It will run as a real Sandvik system. Apply the full engineering process, security review, and the approved deployment route.
About vibe coding
Letting Claude run freely while you go on feel is great for throwaway and experimental work. It is not appropriate for systems others depend on, for sensitive data, or for anything bound for production, where ownership, design and review are not optional.
Good habit: write your intent down by hand in a CLAUDE.md file. Read more about it on the next page.
Working with Claude Code · 3 of 6

Plan and specify first

For anything beyond a trivial change, ask Claude Code to inspect the repository and produce a plan or specification you can review before a single line is written.

Plan mode
$ claude --permission-mode plan
● Plan: add CSV export to report.py
1. read report.py and its tests
2. add an export_csv() function
3. write test_export.py
Approve plan Edit
Why plan first

A plan lets you catch a wrong assumption before it becomes code. You see what Claude understood, which files it will touch, and what it intends to change.

In the terminal you can start with claude --permission-mode plan. In the editor extensions, plan review does the same thing visually.

›State the goal, the inputs, the constraints, and what a good result looks like.
›Read the plan and push back where it misread the task.
›Only approve implementation once the plan matches what you actually want.
Good habit: the more you invest in a clear specification, the less you spend untangling code that solved the wrong problem.
Working with Claude Code · 2 of 6

Instruction files: CLAUDE.md and AGENTS.md

Instruction files tell Claude Code how to work in a repository, so you do not repeat the same context in every prompt. Two files matter most.

CLAUDE.md
Claude Code reads this automatically. It is the natural home for how you want Claude to behave in this project.
AGENTS.md
A shared agent guide many repositories already keep. CLAUDE.md can import it, so there is one source of truth across tools.
CLAUDE.md
# Project guide
@import AGENTS.md
Use our existing test runner.
Keep changes small and explain them.
Ask before adding a dependency.
Keep it clean

An instruction file works best when it is short and intentional. Put your genuine preferences and intent: the conventions you care about, how you want work done, and what to avoid.

Do not overdo it. A file stuffed with everything becomes noise that Claude struggles to weigh. A few clear lines steer it far better than pages of rules.

Never put in these files
No secrets, credentials, tokens, or production data. Instruction files are read every session and are part of the repository, so treat them as visible to everyone who can see the code.
Working with Claude Code · 4 of 6

Stay in control

Claude Code can change files, run commands, and use Git. You decide what actually happens. Review before you approve, every time.

Review changes
report.py
+ def export_csv(rows):
+    return to_csv(rows)
  def build_report():
Approve Reject
Command approval: Claude wants to run npm install. Check what it does, what it touches, and which systems it reaches before you approve.

An unfamiliar command can change files, install dependencies, reach the network, or alter data. Approving it is a decision, not a formality.

Keep Git controlled
›Review the diff before any commit.
›Require approval before commit, push, pull request, or release. Do not let it happen automatically.
›Prefer a working branch over changes straight on the main branch.
Out of scope
Secrets and production data do not belong in a Claude Code session. Never paste passwords, API keys, tokens, private keys, certificates, connection strings, or production data.
Working with Claude Code · 5 of 6

Verify, do not just trust

Tests and a green run are evidence, not proof. Claude can write tests that pass while still missing the point, especially when the same model wrote both the code and the tests.

About AI written tests
Tests from the same model can carry the same wrong assumptions as the code, so they confirm each other rather than the real requirement. Use them as useful scaffolding, then check whether they actually prove the behaviour you intended.
Build a review loop
01Review the plan, then the diff.
02Run the tests and the existing suite, not only the new ones.
03Let CI run, and read what it reports.
04Add independent human review, and a security review where it applies.
When Claude changes security sensitive code, passing tests are not enough. Human review and any required security review still apply. Self review by the same model is not independent review.
Working with Claude Code · 6 of 6

From prototype to shared solution

A useful prototype is a great start. It is not automatically ready for other people to depend on. The jump from your machine to a shared Sandvik solution is a real step, and it has a route.

1
Find an owner. Someone has to be responsible for it over time.
2
Classify the data. Know what it touches, and review the data and security risk.
3
Test it properly and put it through normal engineering review.
4
Use the approved deployment route, such as central deployment through Sandvik Group IT.
A working demo is encouraging, never a release decision. Moving to shared use means moving from casual building to the normal Sandvik process.

Usage and cost

Claude Code is included in the Claude Enterprise plan, with normal usage limits. Longer, context heavy work can go beyond those limits and is then billed pay as you go to your cost center.

Coding work is often context heavy, so it is worth keeping an eye on usage during long sessions.

What drives usage in Claude Code
›Large repositories and long context held across a session.
›Command output and test runs that feed back into the conversation.
›Repeated debugging loops on a stubborn problem.
If you need more capacity
›Request a higher monthly usage or spending limit through the intranet form.
›Expect the higher limit to require approval from your cost approver.
›Your monthly spending limit should be visible in your Claude account.
Not allowed
Do not move Sandvik work into private accounts, personal API keys, or unapproved tools to avoid limits or cost.

Practical scenario

A small script that grows up

A non developer builds a quick helper, the right way, then learns what changes when a colleague wants to use it too.

The person
A planner who is not a developer, but is curious and wants to clean up a messy CSV of their own meeting notes.
The intent
Throwaway. A local helper, run once or twice, with no sensitive data in the file.
Doing it well
01Frame it as throwaway, in a local folder, with only their own non sensitive notes.
02Ask Claude Code for a plan first: read the file, tidy the columns, write a clean copy.
03Review the diff, run it, and check the cleaned file looks right.
The twist
A colleague sees it and asks to use it on their notes too.

The moment someone else relies on it, the intent moves from throwaway to shared. The helper has not changed, but the bar has. Now it needs:

›An owner who is responsible for it.
›A look at the data it might touch once others bring their files.
›Tests, review, and the approved deployment route before it is shared more widely.
Encouraging the planner to build was right. Letting the same casual version spread to others without process would not be. Both ideas live together.
Before it becomes shared, check
An owner is named
Data and security risk reviewed
Tested beyond the original file
Approved deployment route used
